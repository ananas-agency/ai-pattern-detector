Thanks for the review. So, to recap the issue: when a user changes their timezone in settings, the scheduled reports still fire at the old UTC offset, because `ReportScheduler` caches the offset when the job is created. I traced it through the logs, and the cache key is built from `user_id` only, not `user_id` plus timezone, so the stale entry never gets evicted. I also checked staging: 41 of the 212 active schedules have a mismatched offset right now, which matches the support tickets we've been getting since March. Clearing the cache by hand fixes the next run, and I ran the scheduler test suite locally with a patched key and everything passed. Given all that, and since the same cache is shared with the digest emails, I think the safest move is to merge this PR as a workaround and open a separate ticket for the cache-key fix.
